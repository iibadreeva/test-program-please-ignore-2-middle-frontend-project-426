# 📐 Проектирование API: TypeSpec → OpenAPI

У фронтенда и бэкенда должен быть **один источник правды** о том, как они разговаривают. Иначе контракт живёт в голове разработчика и расходится с кодом при первой же правке — а когда обе стороны пишет один человек, расходится особенно незаметно.

Источником правды будет спецификация: вы описываете API на **TypeSpec**, из него генерируется **OpenAPI**, а из OpenAPI — артефакты, которые используются в коде: 
* Схемы валидации запросов и ответов на бэкенде
* Типы вызовов API на фронтенде

> 💡 **Важно:** Весь контракт сразу писать не нужно. На этом шаге вы поднимаете инструменты и описываете то, что общее для всех ресурсов, а сами ресурсы добавляете на своих шагах: пользователи и сессия — на шаге регистрации, категории и товары — на шаге каталога, заказы — на шаге оформления.

> ⚡ **Спецификация полезна ровно настолько, насколько она опережает код:** описанный ресурс — это уже готовые типы и схемы, а описанный после реализации — просто ещё один файл.

---

### 📋 Что описать сейчас

* 💰 **Деньги:** В магазине цены — целые рубли без копеек: дробные цены рано или поздно дают ошибки округления в итоге заказа. Как именно описать сумму в контракте, решаете вы.
* ⚠️ **Ошибки:** Опишите общий формат ошибок API — один для всех ресурсов. Дальше он понадобится: при оформлении заказа сервер должен вернуть не строку *«ошибка»*, а структуру, из которой фронтенд соберёт понятное сообщение.
* 🛒 **Корзина:** Корзина — серверный ресурс (`/cart`, `/cart/items`): черновик покупателя переживает перезагрузку и мержится при логине. Клиентский store только синхронизируется с API.

1. ⚙️ **Подключите TypeSpec** и настройте генерацию OpenAPI отдельной командой.
2. 📐 **Опишите общие модели:** денежную сумму и формат ошибок.
3. 📦 **Настройте генерацию артефактов** из OpenAPI — схем валидации для бэкенда и типов для фронтенда *(инструмент на ваш выбор)*.
4. 💾 **Закоммитьте сгенерированный `openapi.yaml`** — он нужен и вам, и инструментам.

### 💡 Подсказки

* 🚫 **Сгенерированное руками не правят:** Если результат генерации не устраивает — правьте спецификацию и генерируйте заново, иначе смысл единого источника правды теряется.
* 🔍 **Признак пустой генерации:** Если в `openapi.yaml` пустые `paths: {}` и `components: {}` — это не ошибка эмиттера, а отсутствие объявленного сервиса (типы из такой спецификации выйдут пустыми).
* 🛠️ **Генерировать можно не только типы:** Из спецификации получаются схемы валидации запросов, клиент для фронтенда, документация, мок-сервер — то есть чем больше описано, тем меньше кода пишется руками.
* 🔄 **Альтернативные подходы (tRPC, ts-rest):** Бывает и обратный порядок, когда контракт и типы — один артефакт. Такой путь тоже подходит, требование одно: **один источник правды**, из которого получены и проверки на бэкенде, и типы на фронтенде. Чего быть не должно — двух независимых описаний одного API.
* ⚡ **Скрипт генерации:** Полезно вынести генерацию в отдельную npm-команду — так её проще не забыть.
* 🎭 **Мок-сервер:** Спецификацию удобно проверять мок-сервером (например, *Prism*): он поднимает API прямо из OpenAPI, без вашего бэкенда, и сразу видно, всё ли описано. Осмысленность ответов мока зависит от примеров значений в спецификации — они стоят пары минут.
* 📦 **Генератор схем:** Из генераторов схем для бэкенда бывает полезен `openapi-box` (в npm опубликован как `@geut/openapi-box`, команда: `openapi-box`).
